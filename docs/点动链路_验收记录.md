## 一、故障现象
上位机下发点动（写 `40139~44` 目标角 → 置 `40135.Bit0` 触发）后：

- 「运行」位**常亮**（程序确实在运行）
- `40035` 完成位**恒 0**
- 机器人**零位移**
- 触发位**回读确认已送达**（= 1）

⇒ 表面看像"触发送到了但程序没反应"。

## 二、排查路径（每一步都在实机验证，不靠猜）

| # | 假设 | 实验 | 结论 |
|---|---|---|---|
| 1 | 伺服/报警/自动模式等前置不满足 | 读状态 + 一键就绪 | ✅ 正常 → **排除** |
| 2 | 程序没加载 / 没运行 | 加载判据 `Bit11` + 运行位 | ✅ 0.60s 置位、运行位常亮 → **排除** |
| 3 | 触发位不在 `40135.Bit0`（位序与手册相反） | **扫 `bit0`~`bit15`** 逐个触发 | ❌ 16 位全部无反应 → **排除** |
| 4 | 写区变量名不存在 / 映射不符 | **探针程序 201**：`fidbus.mtcp_wo_b[0] := true;` | ✅ `40035` 出现 `True` → **写区映射正确，排除** |
| 5 | 程序里 `WAIT` 的条件写错 | **从示教器导出 200.XPL 看源码** | ★ **命中：两条 WAIT 都等成了「写区」** |

## 三、根因（就差两个字母）

```xml
<set><dest>fidbus.mtcp_wo_b[0]</dest><expr>false</expr></set>
<wait><condition>fidbus.mtcp_wo_b[0]</condition></wait>        <!-- ✗ 等的是刚被置 false 的写区 -->
...
<wait><condition>!fidbus.mtcp_wo_b[0]</condition></wait>       <!-- ✗ 同样错 -->
```

程序第一句把**写区** `mtcp_wo_b[0]` 置成 `false`，紧接着 `WAIT` 去等**同一个变量**变 `true`
→ **永远等不到** → 卡死在 `WAIT`，后面的 `MJOINT` 与置回执都无法执行。

**修法：两处 `mtcp_wo_b` → `mtcp_ro_b`。**

修正后的程序已导入控制器，并于当日从示教器**重新导出**存档：
`C:\Users\Administrator\Desktop\200.XPL`（导出时间 18:52:49 / 示教器钟，对应 PC 16:51）。
复核导出内容确认：第①条 `WAIT` 条件 = `fidbus.mtcp_ro_b[0]`、第②条 = `!fidbus.mtcp_ro_b[0]`，
两条 WAIT 均已指向**读区**，仅 `SET` 回执照旧写**写区** `mtcp_wo_b[0]` —— 即当前控制器上的程序是正确的。

## 五、数据通道（官方手册 15.4.5）

| 方向 | 寄存器 | 程序侧变量 |
|---|---|---|
| PC → 机器人 | `40135` Bit0（点动触发） | `fidbus.mtcp_ro_b[0]` |
| PC → 机器人 | `40139~40144`（J1~J6 绝对角 ×100） | `fidbus.mtcp_ro_i[0..5]` |
| 机器人 → PC | `40035` Bit0（到位回执） | `fidbus.mtcp_wo_b[0]` |

> ⚠ **`ro_*` = PC 写、程序读；`wo_*` = 程序写、PC 读。**
> **`WAIT` 必须用读区 `ro_*`** —— 用写区就等于"自己等自己刚设的值"，必然死等。

## 六、现场踩坑清单

1. **进过示教器的程序编辑态 → 伺服会被下使能**。此时"运行位不置起"是假象，
   先走重吸合流程（`0x0000` → 等 0.6s → `0x1001`）再判断。
2. **程序改动后必须重新加载**（`40104` + 加载命令）才生效。
3. 程序里的 `WAIT` **必须等读区** `ro_*`。
4. **复测前一定要做"防冲预置"**：把 `40139~44` 写成**当前实际角**。
   否则若程序漏写 `WAIT`，一运行就会 `MJOINT` 到残留值
   （实测那里曾是**全 0**，而机器人当时在 J2=-67° / J5=+90° → 等于冲向 0 位）。
5. Modbus 侧**永远读不到程序内容**，涉及"程序里写了什么"的问题只能靠**导出 XPL** 或变量监视。

## 八、★ 第二个坑：「写角度 → 立刻触发」的竞态（完成位秒回、零位移）

### 现象
`tools/jog_axis.py --delta 5 --steps 6` 第一轮 6 步里，**step03 空转**：

```
命令 +5.00°，目标寄存器 = +31.30（读取确认已写入）
完成位在 0.06s 就置 1   ← 快得反常
J6: +26.30 → +26.30，实测位移 0.000°
```

下一步（step04）拿到的起点仍是 `+26.30`，于是目标又是 `+31.30` —— **那一步正常走了**。

### 根因
程序此时**正挂在 `WAIT` 上**。上位机"写完 `40139~44` 立刻置 `40135.Bit0`"，两个写
在同一批次里发下去；控制器**还没来得及把 Modbus 读区同步进程序变量空间**，
`WAIT` 就被放行，`MJOINT` 于是读到**上一轮的旧目标角**（= +26.30 = 当前角）
→ 机器人不动，但程序**照常置回执**（它对"到位"的判断基于它读到的值）。

> 判别特征：**完成位秒回（<0.1s）+ 零位移**。真动作绝不可能是 0.1s。
> 出现条件：时有时无（现场 6 步中 1 次），纯时序竞争。

### 修法（两处都已落地）
1. `tools/jog_axis.py`：写完 → **回读校验** `jog_ro`（`40139~44`）→ **静置 `--settle`（默认 0.15s）** → 才触发。
2. `app/worker.py::_do_jog`：新增 `_verify_jog_target()`，同原理；
   回读不一致时**直接放弃本次点动、不置触发位**（宁可不走，也不发一个不可信的目标）。

### 教训（可推广）
> **任何"写参数 → 置触发位"的通道，中间都必须留一段静置 + 回读校验。**
> 只验证"Modbus 写成功"是不够的 —— 还要确认**程序侧真的看到了新值**。

## 九、★ 点动速度：`40103` 就是闸门（实测，非推测）

同一个程序（`v50perc`）、同一个 5° 位移，只改 `40103`：

| `40103` | 5° 耗时 | 运动段速度 |
|---|---|---|
| **5%** | 3.96s | ≈1.3°/s |
| **100%** | 0.31s | 50~66°/s |

> 结论：**点动速度由 `40103` 控制**，不是由程序里的 `v50perc` 锁死。
> 面板 ④ 卡上每点一次 ± ，`worker._do_jog` 都会先 `set_speed(self.speed)`，
> 所以**界面的「速度」设定同时就是点动速度**。
>
> 换算参考（J6 实测，100%）：**约 60~90°/s ⇒ 想要"转 1 秒"就设 60~90°**。
> 25° 一档时运动段达 **89°/s**（低速档的固定启动/整定开销被摊薄，所以步长越小测出的均速越低）。

另注：`zone = fine` 每步要整定到位，实测**启动延迟 0.09~0.13s**（从置触发位到角度开始变化）。

## 十、采样工具与数据留痕

- `tools/jog_axis.py` 每次运行都把逐点轨迹落 `logs/jog_axis_YYYYmmdd_HHMMSS.csv`
  （列：`tag, t_s, J1..J6`），可直接画曲线复现"到底动没动、多快、有没有抖"。
- 采样频率 ≈ **27 Hz**（单次 `snapshot()` 读齐角位 + `40135`/`40035`，所以足够密）。
- 判定用词：`启动延迟` = 置触发位 → 角度首次偏离起点 >0.05° 的时间；
  `运动段速度` = 位移 ÷（完成位时刻 − 启动延迟）。
